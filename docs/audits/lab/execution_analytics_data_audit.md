# Execution Analytics Platform Data Audit (Sprint 4.6)

This document presents the detailed data and architecture audit of the current execution foundation to support the design and implementation of the Sprint 4.6 Execution Analytics Platform.

## 1. Database Table Inspection

We inspected the active SQLite database schema in [database.db](file:///home/zafka/trade-dashboard/ml_service/storage/database.db) to audit the execution foundation.

### 1.1 `execution_decisions`
This table records every execution decision (both `ACCEPTED` and `REJECTED`) for paper, live, backtest, or research trading.
```sql
CREATE TABLE execution_decisions (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    symbol TEXT NOT NULL,
    direction TEXT,
    decision TEXT NOT NULL CHECK(decision IN ('ACCEPTED', 'REJECTED')),
    reason TEXT, -- RejectReason code (e.g. LOW_CONFIDENCE, MAX_POSITIONS)
    signal_id INTEGER,
    position_id INTEGER,
    confidence INTEGER,
    regime TEXT,
    timeframe TEXT,
    prob_short REAL,
    prob_neutral REAL,
    prob_long REAL,
    execution_edge REAL,
    signal_price REAL,
    execution_price REAL,
    slippage_pct REAL,
    execution_latency_ms INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, 
    source TEXT NOT NULL DEFAULT 'PAPER' CHECK(source IN ('PAPER', 'LIVE', 'BACKTEST', 'RESEARCH')), 
    signal_timestamp INTEGER, 
    execution_policy TEXT, 
    reason_detail TEXT,
    FOREIGN KEY (signal_id) REFERENCES signals(id),
    FOREIGN KEY (position_id) REFERENCES paper_positions(id)
);
```

### 1.2 `paper_positions`
Tracks both open and closed paper trading positions, updated by the Paper Broker.
```sql
CREATE TABLE paper_positions (

    status TEXT NOT NULL DEFAULT 'OPEN' CHECK(status IN ('OPEN', 'TP_HIT', 'SL_HIT', 'EXPIRED', 'MANUAL_CLOSE')),
    realized_pnl REAL NOT NULL DEFAULT 0.0,
    opened_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    closed_at TIMESTAMP,
    confidence INTEGER,
    regime TEXT,
    timeframe TEXT,
    prob_short REAL,
    prob_neutral REAL,
    prob_long REAL,
    execution_edge REAL,
    skip_reason TEXT,
    mae REAL DEFAULT 0.0,
    mfe REAL DEFAULT 0.0,
    mae_timestamp TIMESTAMP,
    mfe_timestamp TIMESTAMP,
    profit_capture_ratio REAL,
    final_exit_reason TEXT,
    trailing_stop_activated INTEGER DEFAULT 0,
    sl_move_count INTEGER DEFAULT 0,
    break_even_triggered INTEGER DEFAULT 0,
    execution_policy TEXT DEFAULT 'FIXED_SL' CHECK(execution_policy IN ('OFF', 'FIXED_SL', 'BREAK_EVEN', 'TRAILING')),
    signal_price REAL,

    execution_timestamp TIMESTAMP,

```

### 1.3 `paper_equity_history` & `paper_account`

```sql
CREATE TABLE paper_equity_history (

```

## 2. Existing Modules Inspection

### 2.1 `ml_service/trading/`
- [execution_audit.py](file:///home/zafka/trade-dashboard/ml_service/trading/execution_audit.py): Defines the `RejectReason` codes and logging logic via the `log_execution_decision()` helper. Crucially, this script bypasses the repository layer, establishing its own SQLite connection to insert directly into `execution_decisions`.
- [paper_broker.py](file:///home/zafka/trade-dashboard/ml_service/trading/paper_broker.py): Governs the paper trading position entry logic. Filters incoming signals using the confidence, regime, and edge gates, and logs corresponding rejections. For accepted positions, it computes sizing, retrieves execution price, inserts directly into `paper_positions`, and fires an execution decision audit log. Bypasses the repository layer using a local `_get_connection()` function.
- [regime_execution_policy.py](file:///home/zafka/trade-dashboard/ml_service/trading/regime_execution_policy.py): Controls whether executions are permitted based on the current regime and confidence.

### 2.2 `ml_service/analytics/`
- [trade_analytics.py](file:///home/zafka/trade-dashboard/ml_service/analytics/trade_analytics.py): Implements pure calculations over `TradePosition` objects, calculating metrics like win rate, gross/net profits, and average hold times. It is fully decoupled from the database.
- [performance_summary.py](file:///home/zafka/trade-dashboard/ml_service/analytics/performance_summary.py): A thin query layer reading model performance stats, but establishes its own raw SQLite connection.
- [live_metrics.py](file:///home/zafka/trade-dashboard/ml_service/analytics/live_metrics.py) & [reconciliation.py](file:///home/zafka/trade-dashboard/ml_service/analytics/reconciliation.py): Directly query the sqlite database to resolve live performance statistics and sync Binance fills.

### 2.3 `ml_service/repositories/`
- [database.py](file:///home/zafka/trade-dashboard/ml_service/repositories/database.py): Exports a database path and connection helper.
- [trade_repository.py](file:///home/zafka/trade-dashboard/ml_service/repositories/trade_repository.py): Interacts with `paper_positions`, but its queries and dataclass definition do not fetch execution quality metadata fields (e.g. `signal_price`, `execution_price`, `execution_timestamp`, `slippage_pct`, `execution_latency_ms`), introducing repository schema lag.
- [signal_repository.py](file:///home/zafka/trade-dashboard/ml_service/repositories/signal_repository.py): Queries signals.
- [equity_repository.py](file:///home/zafka/trade-dashboard/ml_service/repositories/equity_repository.py): Queries equity history snapshots.
- **Missing Repository**: There is no repository abstraction for `execution_decisions`, making querying or aggregation of rejections awkward and fragmented.

## 4. Key Architectural Checks

### 4.1 Missing Columns
- The `TradePosition` mapping in `trade_repository.py` is missing the execution quality columns (`signal_price`, `execution_price`, `execution_timestamp`, `slippage_pct`, `execution_latency_ms`). While they exist in the DB schema, the repository logic cannot access them, leading to **repository lag**.

### 4.2 Schema Drift
- The base migration files `026_restore_complete_schema.sql` do not contain the execution columns (`signal_price` etc.) in their `CREATE TABLE` structure, but they were altered manually or via tests, resulting in schema drift. These columns must be formalised in repositories and migrations.

### 4.3 Duplicate Sources of Truth
- **Execution Quality Attributes**: Slippage, latency, execution price, and signal price are duplicated across `execution_decisions` and `paper_positions` for accepted trades. While this is helpful for instant position-level metrics, it introduces data consistency risks.

### 4.4 Repository Boundaries
- **Bypassed Connections**: `paper_broker.py`, `execution_audit.py`, and multiple analytics modules bypass the `repositories/database.py` connection management and write raw SQL directly.
- **Missing Execution Decisions Repository**: There is no standard repository mapping for the `execution_decisions` table.

### 4.5 Data Lineage Problems
- Realized trades synced from the exchange are loaded into `user_trade_history`, whereas paper trades exist in `paper_positions` / `execution_decisions`. The analytics platform must handle both sources cleanly without mixing live/paper lineage.

### 4.6 Production Readiness
- Core data is present and correctly typed. Relational indexes exist on symbol, status, and created_at timestamps. No blocking database errors were detected.

---

## 5. Final Verdict

### Verdict: READY FOR DESIGN

While the platform has architectural flaws (repository lag, direct SQL writes, bypassed connection managers, and duplicate execution stats), the underlying data structures for Sprint 4.6 are **fully populated and active**. There are no schema or data blocks preventing the design of the analytics dashboard and service layers.

> [!IMPORTANT]
> The design phase should prioritize:
> 1. Restructuring `TradeRepository` to map all execution quality attributes.
> 2. Creating an `ExecutionDecisionRepository` to consolidate funnel rejections.
> 3. Standardizing database connection management to avoid duplicate sqlite connections.
