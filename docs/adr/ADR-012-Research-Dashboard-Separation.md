# ADR-012: Separation of Research Dashboard Layer and Live Systems

## Status
Proposed (Design Only)

## Context
As the MoroQuant platform matures, the volume of quantitative research experiments, datasets, and feature configurations scales rapidly. Researchers need a workspace to track, inspect, compare, and analyze historical research experiments without modifying frozen results or interfering with live trading systems.

Without clear architectural separation:
1. Research inspection tools might run heavy statistical queries directly against live databases or transactional systems, causing latency spikes.
2. Code path leakage might allow temporary dashboard-driven evaluation code or metric recalculations to corrupt historical or immutable experiment records, violating the principle of research reproducibility.
3. The UI layer could couple live trading components (order books, open positions) with research workflows (backtest comparisons, statistical distribution checks), leading to a cluttered user experience and fragile code dependencies.

To prevent these issues, we need a dedicated, read-only Research Experiment Dashboard layer built on top of our existing immutable datasets and metadata registry.

## Decision
We will separate the Research Experiment Dashboard into a self-contained module conforming to the MoroQuant architecture (`Repository -> Service -> Analytics -> API -> Frontend`), governed by the following constraints:

### 1. Read-Only Integrity
* The Research Dashboard is strictly a "window" into the research system.
* It must not modify any datasets, feature definitions, version files, experiment registries, or evaluation logs.
* No data mutation APIs (`POST`, `PUT`, `DELETE` on core schemas) will be exposed except for stateless utility endpoints (e.g. `POST /research/experiments/compare` which computes comparison matrices on-the-fly).

### 2. Architectural Structure and Module Boundary
All backend code for the research dashboard will reside in `ml_service/research/dashboard/` and follow the standard MoroQuant layer separation:
* **Repository (`repository.py`)**: Interacts with metadata databases to read experiment runs, datasets, and feature lineages.
* **Service (`service.py`)**: Orchestrates data loading and aggregates data across different modules.
* **Analytics (`analytics.py`)**: Performs read-only statistical computations (e.g., metric comparisons, rankings, distribution shifts) on the loaded metadata.
* **API (`api.py`)**: Formulates the web API layer using strict schema verification.

### 3. Decoupling from Live Systems
* The Research Dashboard will read from the frozen files and metadata generated by the **Dataset Manager** and the **Feature Store**.
* It does not contain any trading execution APIs or live monitoring socket connections.
* It is restricted to historical experiment artifacts (Parquet logs and SQLite metadata).

## Consequences
* **Benefits**:
  * **Absolute Integrity**: Guarantees that historical research truth remains completely unchanged.
  * **System Performance**: Isolates heavy analytics/comparisons from hot execution paths.
  * **Separation of Concerns**: Prevents quantitative research visualization libraries and components from leaking into the lightweight trading client.
* **Trade-offs**:
  * Dual-schema dependency: If experiment metadata structures change, the Research Dashboard repository layer must be updated. This is handled using robust semantic contracts.
